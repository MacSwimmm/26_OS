# 韩臻浩答辩与现场演示

## 启动前

在仓库根目录确认 Python 3.10+，执行：

```bash
python3 -m unittest discover -s tests -v
python3 dashboard_server.py
```

浏览器打开 <http://127.0.0.1:8765>。保持终端可见，首次停在 t=0。上位机“控制台设置”可调整动效，投影掉帧时关闭“功能区悬浮震颤”和“动态点阵”。保存过旧设置时可恢复默认。

## 建议顺序（约 5–7 分钟）

1. **普通运行与并发**：点击开始，再暂停并拖到 t=1。T1 使用通道，T2 使用茶歇台；T3 因依赖 R1 等待。说明默认按资源并发，不虚构固定人数限制。
2. **紧急抢占**：拖到 t=2，查看事件日志。U1 到达，低优先级 T1 保存阶段和剩余时长并释放资源；U1 于 t=4 完成，T1 随后继续。对比非抢占/FCFS，紧急任务会超期，普通任务仍完成。
3. **故障与环境**：t=3 茶歇台故障，T2 暂停而占用保留；t=5 茶歇台恢复，同时通道关闭使 T1 暂停；t=7 通道恢复。可在资源和事件标签交叉核对。
4. **事件与依赖**：t=6 杯子事件创建 R1，t=7 的同杯子重复事件被忽略。R1 于 t=12 完成后，T3 才能执行，t=14 全部完成。
5. **死锁三项机制**：选择“死锁避免与恢复”。同一输入中，避免组 2/2 完成且环为零；只检测组检测 1 次并到 H 导出；检测并恢复组回滚 1 次、丢失并实际重做 1 单位，最终 2/2 完成。
6. **展示代码对应**：打开 `policies.py`、`deadlock.py`、`scheduler.py`，分别解释排序、试分配/环、状态保存与恢复；展示 JSON 导出和 `metadata` 中的版本及摘要。

视效展示放在功能说明之后：移动鼠标扫过标题、指标，滚到页底扫过大字；设置里分别关闭，证明动效不影响按钮、键盘和仿真数据。

## 终端备用

```bash
python3 run_demo.py --scenario baseline --live --delay 0.2
python3 run_demo.py --scenario deadlock --view trace
python3 run_demo.py --input data/demos/basic.json --view trace
```

`basic.json` 可以手算：A 执行 [0,2)，B 等待前置完成，再执行 [2,3)，完成时刻分别为 2 与 3。窗口 H=10，茶歇台有效利用率为 3/10。

## 应当能回答的问题

- **竞争和死锁区别？** 普通等待可能自然解除；单实例资源的循环等待需要避免或破解。依赖环是输入错误。
- **为什么银行家还要检测？** 正常配置提前避免危险分配；关闭避免的压力场景用于单独验证检测/恢复。避免组零死锁不能证明检测没实现。
- **中断时为何有时释放、有时不释放？** 调度抢占在允许位置主动让出；故障暂停保留原占用，资源恢复后继续，不把正在转移的原子步骤强行拆开。
- **回滚会不会把不可逆工作重复执行？** 只允许显式可回滚的任务；演示使用可逆预留。检查点后损失与实际重做分别计数。
- **为什么利用率很低？** 固定 H=200，小演示很早完成，之后空闲仍计入分母；不能用执行结束时刻缩短窗口提高数字。
- **是不是 Linux 内核或多线程实现？** 单进程离散时间模型，在 Linux 上运行并验证操作系统概念。
- **能保证高分或策略最优吗？** 依据项目说明逐项覆盖并提供测试证据；得分还取决于正式实验、报告、现场与教师评分，当前没有最优性证明。
