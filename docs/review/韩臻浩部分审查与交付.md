# 韩臻浩部分：审查、修复与交付

审查日期：2026-11-08。原始项目提交：`f02a18f57d7cb2a830809a83d43b0d6a224ede3f`。依据：《茶歇服务员任务调度项目说明》第 13、17 节；审查对象为公共模型、引擎、中断、抢占恢复、死锁核心、集成测试、演示和对应文档。上位机另按用户指定模板最新源码移植。

## 结论

原版本具备可运行骨架，原有 8 项测试通过，但不适合直接声称“韩臻浩部分已完备”。存在会影响模型一致性、统计公平性与现场讲解的真实缺陷。下表所列功能缺项和实现缺陷已补齐，并经回归验证；目前可作为韩臻浩核心实现与演示材料交接版本。

完整课程项目仍需要正式实验统计、教师模板论文、参考文献、各成员核对及目标机器现场验收。软件验证不能保证分数，也不能替代这些交付。

## 主要发现与修复

| 原问题 | 影响 | 本轮处理与证据 |
|---|---|---|
| 故障/环境和主动抢占共用“释放所有资源”暂停 | 违背保留占用模型，可能让原子步骤失去资源 | 分离语义；故障保留、抢占释放；验证故障中占用和进度 |
| 故障只查当前阶段声明，未查前阶段保留资源 | 任务可能在持有故障资源时继续工作 | 联合检查真实占用与阶段需求；覆盖保留资源故障 |
| 抢占后只申请当前阶段新增资源 | 跨阶段已释放的保留资源可能无法重建 | 按历史阶段释放规则重建完整需求；验证恢复申请 x+y |
| 紧急抢占仅在到达瞬间尝试 | 紧急任务换阶段后可能长时间等资源 | 每步对符合条件的高优先级候选检查安全抢占 |
| 缺少 FCFS，排序与引擎耦合 | 必要基线和成员接口缺失 | 新增纯排序 `policies.py`、FCFS 场景和并列案例 |
| 默认固定 2 个执行者，与说明中无人数约束不一致 | 存在隐藏调度约束 | 默认 `workers=None`；显式保留可选扩展 |
| 普通业务为整包资源、故障演示可能没有实际暂停 | 难以验证分阶段与三类中断 | 重建三类业务阶段；固定基线实际触发抢占、环境、故障 |
| 普通事件、杯子去重和共享只读公告板缺失 | 项目说明中的业务/共享资源不完整 | 增加 request/cup_taken、cup_id 去重和不可变快照 |
| 输入只校验部分依赖，事件任务/资源等检查不足 | 错误在运行中才出现或无法解释 | 到达任务合并预检，校验时间、Max、容量、释放、开关和依赖 |
| 关闭银行家时可绕过最大需求验证 | 错误请求可能污染所有权账本 | 资源合法性始终先查，非法申请原子失败 |
| 利用率随提前结束缩短分母 | 各组统计窗口不公平 | 使用固定 H，补齐空闲尾段，保留原始分母 |
| 持有等待计入有效工作、故障与冲突混计 | 利用率和冲突数失真 | 有效使用、持有、故障、故障中持有分别记录 |
| 紧急错失率用全部紧急任务作分母 | 截止时间超过 H 的任务稀释错失率 | 分母仅取已到达且截止时间 ≤H 的任务 |
| 缺少按时率和未完成明细，空值口径不一致 | 完成均值可能掩盖失败 | 补按时率、unfinished、null、原始资源时间 |
| 回滚选择依据剩余时长，重试缺少避免重复成环策略 | 与重做成本规则不符，可能重复死锁 | 按优先级/检查点损失/id；重试原子预留 Max |
| 检查点未随安全阶段推进，损失和实际重做混淆 | 恢复材料不足以复核 | 无持有时推进检查点，分别记录损失和真实重做 |
| 快照在步执行后标为 t，甘特图反推执行 | 页面完成时刻和任务进度可能提前 | 改为执行前边界快照与终止帧，按运行状态画区间 |
| 页面把故障不可用画成资源已占用，阶段进度用 remaining 反推 | 展示与真实账本/总工作量不一致 | 使用 holders 和 completed_work；共享公告板单独处理 |
| no_dynamic 同时改变重排与抢占配置，关闭死锁还关闭观测 | 因果解释含混 | 只改声明变量，检测保留；文档明确策略语义联动 |
| 没有外部场景加载/CSV/充分版本追溯 | 成员难以准备输入与复现实验 | 增加 JSON/CSV、输入与源码摘要、种子、Git 版本 |
| 分工表错置核心算法职责且姓名有误 | 答辩贡献和接口交接错误 | 按共同项目说明纠正并写出真实路径 |

## 本轮核验

- 52 项 Python 自动检查：原有测试、输入、排序、中断、边界、死锁、检查点、统计及真实 HTTP 服务。
- Ubuntu 24.04.2 上的 Python 3.12.3 和独立 CPython 3.10.21 均通过。
- 21 项浏览器检查：播放/防重入/暂停/倍速/单步/拖动/重跑、场景、五策略、死锁三组、返回续播、设置、模块显隐、焦点、重试、导出、宽度与新增动效。
- 100 次混合负载回归：种子 1—20 × 五种策略，同种子共享 workload 摘要、统一 H；内部资源不变量与总工作量检查通过。
- `basic.json` 手算：完成边界 A=2、B=3，茶歇台有效工作 3，固定 H=10，利用率 0.3。
- 死锁：避免组 2/2、0 死锁、1 安全拒绝；只检测组 0/2、1 死锁、到 H 导出；恢复组 2/2、1 回滚、损失和实际重做各 1。
- 全部 CLI 固定演示、场景加载和 JSON/CSV 导出实跑；JS 语法和 `git diff --check` 检查。

本地 Ubuntu 22.04 容器验证因 Docker Hub 镜像拉取超时未执行；已加入 GitHub Actions 的两个 Python 环境和浏览器检查，最终以对应提交的实际运行记录为准。详细本机证据见 `validation.json`、`browser-validation.json` 与图像；完整中间结果可用说明中的命令重建。
