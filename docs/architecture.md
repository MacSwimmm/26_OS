# 系统架构与算法说明

## 1 场景模型

茶歇服务员处理递送水杯、整理茶歇台、回收空杯和补充杯子四类任务。`Task` 是论文中的任务结构体：

\[
T_i=(p_i,d_i,e_i,Pre_i,R_i,preemptible_i)
\]

其中 `p` 是优先级，`d` 是截止时间，`e` 是执行时长，`Pre` 是前置任务集合，`R` 是资源需求。茶歇台、取杯区、回收区和通道建模为互斥资源；资源容量大于 1 时可以表示多个并行位置。

## 2 调度流程

1. 静态阶段按照“紧急标记、优先级、截止时间、提交时间”形成初始顺序。
2. 动态阶段每个时间片处理到达的中断、检查依赖、尝试原子申请资源，并为等待任务记录冲突。
3. 抢占模式下，紧急请求到达时保存被抢占任务的 `remaining`，释放资源；中断结束后按相同规则恢复。
4. 非抢占模式保持当前任务直到完成，用于和抢占模式做公平对比。

## 3 死锁三件套

- **避免**：`deadlock.py` 的 `request_is_safe` 先试分配，再调用银行家安全性算法；不安全请求只进入等待队列。
- **检测**：根据资源分配表和等待请求表建立等待图。若 DFS 找到环，则记录死锁次数。
- **破解**：从环中选择优先级最低且剩余工作量较小的任务，优先回滚并释放资源；不可安全回滚时撤销任务。恢复动作和被选任务会写入轨迹。

典型环是：任务 A 占用茶歇台等待回收区，任务 B 占用回收区等待茶歇台。运行 `python3 run_demo.py --scenario deadlock` 可得到该资源分配图对应的等待图和环。

## 4 中断模型

`InterruptType` 分为紧急服务请求、环境扰动和故障中断。紧急请求会动态加入任务队列并尝试抢占低优先级任务；环境中断暂时封锁通道并保存受影响任务；故障中断可以撤销指定任务并释放其资源。每条中断和恢复动作都写入 `trace`，便于论文画时序图。
