# 架构与核心算法

## 模型和模块

A 占茶歇台、B 等茶歇台是普通竞争；只有 A 持台面等回收区、B 持回收区等台面，才构成资源死锁。依赖未完成、资源故障和安全性拒绝都有单独原因，不混入死锁图。

| 模块 | 职责 |
|---|---|
| `models.py` | 输入校验、Task/TaskStage、事件、状态、配置和指标 |
| `policies.py` | 纯排序函数；不修改任务、资源或进度 |
| `scheduler.py` | 到达、依赖、时钟、分配、中断、抢占、执行和回滚集成 |
| `resources.py` | 原子申请/释放与所有权；调用银行家检查 |
| `deadlock.py` | 安全序列、试分配、等待图、环和回滚对象排序 |
| `scenario_io.py` | JSON 输入、输入/源码摘要、版本与种子 |
| `scenarios.py` | 固定业务与死锁输入、单变量对照配置 |
| `dashboard_server.py` | HTTP API 与边界快照，不重写算法 |

任务模型为 `Ti=(ai, pi, di, Si, Di, qi)`，分别表示到达、优先级、截止时间、阶段、依赖和是否可抢占。`Task.duration` 必须等于阶段时长总和。阶段中的 `resources` 表示本阶段需要达到的持有量；上一阶段未释放的资源继续保留，申请接口仅提交差额。单阶段 `Task.resources` 仍可使用。

默认并发只受资源约束，`workers=None`。`workers` 是显式可选扩展，所有对照组必须保持一致；不将默认仿真解释为固定人数的服务员系统。四个互斥资源的代码名为 `tea_table`、`cup_station`、`return_station`、`corridor`；`request_board` 为共享只读快照，不占互斥容量。

## 时钟和状态

边界 `t` 先处理到达、关闭/恢复和依赖，再排序、申请、检测死锁，随后执行 `[t,t+1)`，完成记录使用 `t+1`。上位机在执行前采样，因此 t=0 时工作量为零，t=4 完成的任务不会出现在 t=3 的完成数里。最后额外采集一个终止边界。

达到 H 后仍登记 H 时刻的事件和到达，允许记录恰好在 H 完成的任务，停止新增执行。若任务与窗口内事件提前结束，实际执行时间可以小于 H，统计分母仍补齐到 H。

输入说明中的 NEW/WAITING/DONE/CANCELED，分别映射为 `pending/blocked/completed/cancelled`。依赖等待使用 `blocked` 和 `waiting_reason="dependency"`；资源等待原因另记。超时为软截止时间，不自动取消任务。

## 排序和抢占

FCFS 按 `(arrival, id)`；优先级按 `(-priority, deadline, arrival, id)`。静态模式固定 t=0 已知任务的初始顺序，后续到达追加；动态模式只对已到达且依赖满足的任务重排。队首缺少资源时继续尝试其他候选任务，避免无关资源闲置。

动态优先级模式开启抢占后，高优先级就绪任务可以暂停相关的低优先级运行任务；任务和当前阶段都必须可抢占。紧急请求考虑其声明的后续最大资源需求，以便在进入取杯阶段前让出配送通道。FCFS、静态和非抢占配置均不主动抢占。

抢占保存阶段与剩余时长并释放互斥资源。恢复会重建此前跨阶段保留的资源需求，重新申请成功后继续，已完成工作保持不变。日志中的 `pause.resources_released` 和 `resume.acquired` 可核对这一过程。

## 故障与环境中断

有限资源故障/通道关闭暂停持有该资源的任务，包括已进入下一阶段、仍保留该资源的任务；不受正常可抢占标记限制。暂停保存进度并保留占用，故障期间不推进工作，也不把资源转给其他任务。

任务必须等待涉及的所有资源恢复。重叠关闭取最晚结束；`restore` 表示显式恢复资源当前全部关闭状态。资源自动恢复、显式恢复和任务恢复均有日志。任务定向故障也可通过 `target_task_id` 表示，必须给出有限时长。

## 死锁避免、检测与破解

银行家检查使用 `Need=Max-Allocation`。先检查资源名、正整数请求、Max 和容量，再检查故障和真实可用量，最后试分配、查安全序列；失败不修改账本。Max 采用整个任务的保守需求，可能包含已用完的资源，因此会降低并发；这属于需要在论文讨论的代价。有限故障由暂停机制处理，安全序列使用物理容量，并假设资源按输入恢复。

检测只使用实际因“已占用”而等待的请求构建任务等待图。资源是单实例时，图中环意味着循环等待。遍历顺序固定；同一组任务的持续环只计一次。禁止将本实现直接扩展为多实例后继续用环作充分判据。

破解只选择环中 `rollback_allowed=True` 的任务，按“最低优先级、最少检查点后重做量、编号”排序。安全检查点在阶段结束且任务已释放全部互斥资源时推进。回滚释放真实占用、恢复阶段/进度，记录损失；重试将 Max 按资源名排序后原子预留，全部可得才提交，并保留到完成，防止重新形成同一个部分持有等待环。该方法保守，可能牺牲并发。

超过重试上限时撤销任务；没有可回滚对象时记录“未解除”，仍可到 H 导出。`rollback_work` 是丢失量，`redo_work` 是后续确实执行的重做量，窗口提前截断时两者可以不同。死锁演示只使用允许回滚的合成预留步骤，不能把不可逆的业务操作随意回滚。

## 正确性保障

引擎每个执行边界检查：占用不超过容量、运行任务具备全部需求、依赖已满足、故障资源不被执行、完成/未来任务没有占用、运行集合无重复。构造时检查编号、依赖图、事件任务、资源声明、释放规则、时长与开关类型。输入对象深复制，每次实验必须创建新引擎。

具体行为由 `tests/test_engine_contract.py`、原有 `tests/test_scheduler.py` 和真实 HTTP 检查 `tests/test_dashboard_api.py` 验证。
