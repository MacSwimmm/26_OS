# 茶歇服务员任务调度项目说明

组长：韩臻浩\

本项目采用 Python 实现茶歇服务任务调度仿真系统，在 Linux 环境中验证任务调度、资源竞争、死锁处理和中断响应机制，并通过对比实验形成课程论文。本说明面向全体项目成员，统一项目范围、任务模型、模块接口、实验方法、职责分工和验收标准，作为开发、测试与报告编写的共同依据。

## 2 项目目标与典型场景

典型调度场景如下：任务 A 正在整理茶歇台，任务 B 因需要使用同一台面而等待。此时紧急送水任务 C 到达，系统根据优先级、可抢占条件和资源可用状态，确定 C 的执行时机以及 A 是否暂停。

典型死锁场景如下：任务 A 占用茶歇台并申请回收区，任务 D 占用回收区并申请茶歇台，双方形成循环等待。系统应能够通过安全性检查避免危险分配，或在关闭避免机制的验证场景中检测等待环并执行恢复措施。

项目应明确展示任务等待、选择、暂停和恢复的原因，并通过实验比较不同策略对完成率、时延、资源使用和恢复成本的影响。

## 3 系统模拟范围

### 3.1 并发模型

系统采用单个 Python 进程实现离散时间仿真。多个虚拟任务流程可同时存在，并在资源无冲突时并发推进。仿真引擎按统一时间步更新任务，无需依赖真实多线程或多进程。

模型以并发的服务请求和维护活动为调度对象，不单独设置服务员人数约束。实验结论适用于本说明定义的抽象服务系统，论文应说明该适用范围。若扩展人员数量约束，应将人员容量纳入模型，并重新验证调度与死锁逻辑。

并发任务通过交错申请和保留资源形成竞争条件。完全串行执行无法充分验证循环等待，因此不作为本项目的并发模型。

### 3.2 时间与参数

- 一个时间步记为 1 个模拟时间单位，与现实时间不作直接换算。
- 任务执行时长由场景配置给定，实验中注明其为模拟参数。
- 默认仿真观察上限为 H=200；任务时长等参数经小规模验证后确定，并写入正式实验配置。
- 各对比组使用相同观察时长，到 H 时仍未完成的任务应完整记录。
- 允许在 H 时刻记录恰好完成的任务；不再执行 H 之后的工作。

### 3.3 成果形式

系统提供命令行运行入口、逐事件日志、CSV/JSON 结果和静态图表。图表可采用标准库生成 SVG，以减少环境依赖。登录管理、数据库、三维场景和机器人控制不在项目范围内。

## 4 任务模型

### 4.1 三类任务

正常业务任务采用下表所列步骤。资源在需要时申请，并按步骤规定释放或保留。

| 类型 | 任务类别 | 执行步骤 | 默认优先级 |
|---|---|---|---|
| 递送水杯 | 服务请求 | 取杯区取杯 → 释放取杯区 → 使用通道配送 → 释放通道 | 普通 2；紧急 3 |
| 整理茶歇台 | 维护整理 | 申请茶歇台 → 整理 → 释放台面 | 1 |
| 回收空杯 | 维护整理 | 使用通道到达 → 释放通道 → 占用茶歇台收集 → 申请回收区完成转移 → 释放相关资源 | 1 |

优先级数值越大表示优先程度越高。普通回收任务的优先级可通过配置调整，同一对比实验中应保持一致。

回收任务依据杯子编号与“杯子已取走”事件创建，同一杯子在本次回收流程中只创建一次任务，重复事件不得重复触发。该关系采用题目给定的事件简化模型，不包含饮用过程的建模。

### 4.2 任务数据字段

| 字段 | 含义 |
|---|---|
| id、type | 任务编号、类别 |
| arrival_time | 任务到达时刻 |
| base_priority | 基础优先级 |
| deadline | 最晚完成时刻 |
| dependencies | 执行前必须完成的前置任务集合 |
| stages | 执行步骤、各步骤时长及资源申请、保留和释放规则 |
| max_claim | 整个任务最多可能同时占用的资源上界，供安全性检查使用 |
| preemptible | 是否允许被调度抢占；同时受当前步骤规则限制 |
| rollback_allowed | 是否允许回滚，与可抢占属性分别定义 |
| state | 当前任务状态 |
| stage_index、remaining_time | 当前步骤编号及剩余执行时长 |
| held_resources、waiting_request | 已占用资源及当前等待的资源请求 |
| start_time、finish_time | 首次开始与最终完成时间 |
| checkpoint、retry_count | 恢复检查点及重试次数 |

截止时间采用软截止时间：超时任务仍可继续执行，并保留超时记录。任务完成率与按时完成率分别统计。

前置依赖表示“前一个任务完成后才允许开始”，例如回收完成后再开始一次最终台面整理。输入必须检查依赖对象存在、依赖图无环。依赖环属于输入错误，不算资源死锁。

### 4.3 任务状态

```text
NEW       已登记，还没到达
READY     已到达且依赖满足，等待选中
RUNNING   正在执行某一步骤
WAITING   等待资源或前置依赖，必须记录原因
PAUSED    因抢占/中断暂停，进度已保存
DONE      已完成
CANCELED  已撤销，不再执行
```

超时是额外标记，不必把任务直接取消。WAITING 与 PAUSED 不同：前者缺少执行条件，后者是被主动暂停。

## 5 资源模型

### 5.1 资源分类

| 对象 | 容量与访问规则 | 说明 |
|---|---|---|
| 茶歇台 TABLE | 1，互斥 | 同一时刻只允许一个任务操作 |
| 取杯区 PICKUP | 1，互斥 | 简化为单个取杯操作位置 |
| 回收区 RECYCLE | 1，互斥 | 指回收操作位，不模拟无限堆积或垃圾桶容量 |
| 通道 PASSAGE | 1，互斥 | 简化为单条窄通道，不实现空间寻路 |
| 请求公告板 REQUEST_BOARD | 共享只读 | 多任务可读取请求/位置资料，不构成互斥瓶颈 |

公告板由引擎在时间步开始时统一更新快照，任务仅访问只读快照。共享只读对象不纳入死锁资源图。

四种互斥资源均采用单实例，可通过资源分配图的循环等待识别死锁。若扩展为多实例资源，应相应调整检测算法，图中存在环不再作为充分判定条件。

### 5.2 申请、保留和释放

1. 任务到当前步骤后提出资源申请。
2. 检查资源是否空闲、是否因环境或故障不可用。
3. 开启死锁避免时，再进行银行家安全性检查。
4. 允许才更新资源归属，否则进入等待并记录原因。
5. 步骤完成后按配置释放资源；需要跨步骤保留时必须明确标注。
6. 不允许无条件抢走另一个正常运行任务的资源。

资源竞争通过等待、可执行任务重排及资源释放后重试处理。绕行和临时增加资源不在当前实现范围内，论文按实际实现描述处理策略。

## 6 调度规则

### 6.1 先来先服务 FCFS

候选任务中按到达时间选择；相同时按任务编号排序。未满足依赖或缺少资源的任务不得执行，不可因为队首被阻塞就永久闲置其他可用资源。

### 6.2 优先级调度

候选任务按优先级从高到低选择；相同时依次比较截止时间、到达时间和编号。系统采用固定优先级，长期等待任务的老化加分可作为后续扩展，纳入实验前需完成实现与验证。

算法不仅要返回选择结果，还应记录原因，例如“紧急任务优先”“同优先级，截止时间更早”。

### 6.3 静态预调度与动态重调度

静态模式：对 t=0 已知任务生成初始顺序，后续新任务按到达顺序追加，不因紧急程度重新排序；仍然执行基本资源检查，仍然记录事件和故障。

动态模式：在新请求、中断、资源恢复、任务完成等事件后重新评估候选队列。不能提前知道未来尚未到达的请求。

静态模式面对事件也应作最基本处理，不应故意漏接任务或无视资源故障来制造差距。两组只改变重排策略。

### 6.4 可抢占与不可抢占

非抢占模式：正常工作步骤一旦开始，执行完该步骤再切换。故障暂停属于被迫中止，与主动调度抢占分开记录。

可抢占模式：只允许在任务和当前步骤均允许的安全位置暂停，并保存阶段、剩余时长和恢复信息。可抢占步骤暂停时释放互斥资源，恢复时重新申请。需要保留资源的原子转移步骤标为不可抢占。

抢占实现应同时包含运行状态切换、进度保存和恢复；恢复后保留已完成的有效工作量。

## 7 死锁避免、检测和破解

### 7.1 避免方法

死锁避免采用银行家安全性检查。系统维护各互斥资源的总量、可用量、任务当前占用和最大需求；每类互斥资源总量为 1。

资源申请首先接受最大需求校验，再进行试分配，使用 Available、Allocation、Max、Need 检查是否存在使当前任务全部完成的安全序列。检查通过后提交分配，否则撤销试分配并将任务置为等待状态。资源空闲检查与安全性检查分别执行。

Need = Max - Allocation。Max 应覆盖任务后续可能提出的需求，且不超过系统总容量。最大需求采用保守上界可能降低并发程度，论文应分析该影响。资源故障期间暂停新分配，恢复后重新检查；故障响应由独立的中断机制处理。

### 7.2 检测方法

每个时间步申请和执行更新后，依据当前真实占用/等待关系更新资源分配图：任务 → 资源表示请求，资源 → 任务表示占用。使用图遍历检测循环等待。

资源图仅包含当前实际提出的申请与占用关系。故障、通道关闭、前置依赖和普通排队分别记录等待原因，死锁判定依据实际循环等待关系进行。

### 7.3 破解方法

死锁破解采用任务回滚：选择可回滚任务，恢复至检查点并释放其持有资源。优先选择环中优先级最低的可回滚任务；相同时按较少重做成本、任务编号确定，并记录选择原因。

回滚丢失的检查点后工作量及其重做时间应计入仿真。回滚任务重试时按统一资源顺序获取所需资源，必要时等待，以避免立即重建相同等待环。系统设置最大重试次数，超过后撤销任务并记录原因。若环中没有可回滚任务，输出“未解除”，保留未完成状态。

可暂停、可回滚是两个不同属性；正常业务中不可逆的步骤不能随意回滚。演示死锁使用明确允许回滚的虚拟预留步骤。

### 7.4 专项验证场景

| 场景 | 配置 | 预期验证结果 |
|---|---|---|
| 正常排队 | 任意正常配置 | 等待后恢复，没有错误报警 |
| 无保护死锁 | 关闭避免、关闭破解，保留检测 | A 占 TABLE 等 RECYCLE；B 占 RECYCLE 等 TABLE；检测到环 |
| 检测后破解 | 关闭避免、开启检测和回滚 | 同一输入能发现环、释放资源、继续执行 |
| 提前避免 | 开启安全性检查 | 同一输入的危险申请被延后，不形成该环 |

死锁验证场景通过正常的任务步骤与资源接口建立：两个任务先分别持有不同资源，再申请对方持有的资源。验证过程不得通过绕过接口改写内部状态制造结果。相反的资源申请顺序属于受控压力条件，应与正常业务场景分别说明。

死锁避免、检测和破解分别设置验证配置。避免机制有效时允许死锁次数为零；检测与破解通过关闭避免机制的受控场景验证。

## 8 事件和中断

| 事件 | 处理方式 |
|---|---|
| 普通送水请求 | 创建新任务；根据调度模式入队 |
| 紧急送水请求 | 创建高优先级、有截止时间的任务；动态模式检查是否安全抢占 |
| 客人取走杯子 | 创建该杯子的回收任务，保证不重复 |
| 通道暂时关闭 | 阻止新的通道申请；正在通行的步骤保存进度并暂停，保留通道占用直至恢复 |
| 操作位故障 | 故障操作位暂停服务，受影响步骤保存状态，其他可执行任务继续 |
| 资源恢复 | 清除不可用标记，恢复条件检查后继续，不重复计算已经完成的工作 |

故障建模为有限时长的资源不可用，不涉及物理损坏或维修人员调度。暂停期间不推进该步骤工作量。保留占用的不可中断任务持有的资源不得被普通任务强行分配；占用时间、有效工作时间和故障时间分别记录。

随机事件先按种子生成事件文件，各算法读取同一份文件。不允许每个实验组自行抽取不同随机请求再直接比较。

## 9 仿真运行流程

```text
读取配置、任务和事件，检查编号、依赖、时长、资源需求
    ↓
在 t=0 建立初始任务队列
    ↓
每个时间步 t：
    1. 处理到达、关闭、故障和恢复事件
    2. 更新已满足的依赖和暂停恢复条件
    3. 根据调度策略分配执行机会、处理安全抢占
    4. 检查资源申请，更新等待与占用关系
    5. 可运行步骤执行区间 [t, t+1)
    6. 在 t+1 处理完成、释放、检查点及新状态
    7. 检测死锁并按配置恢复，记录日志和指标
    ↓
任务和未来事件均结束，或到统一观察上限 H
    ↓
输出任务结果、事件日志、汇总指标和运行配置
```

同一时刻多个任务申请同一资源，按当前调度排序依次裁决，保证相同输入与配置下结果可复现。同一步结束后，等待任务从下一时间步重试，避免时间步内重复申请造成无限循环。

## 10 指标定义

统计任务集取本次观察窗口内已经到达的所有任务，包含由事件生成的任务；未来未到达任务不进分母。固定任务输入、种子和观察上限，所有组使用相同口径。

| 指标 | 本项目定义 |
|---|---|
| 任务完成率 | 截至 H 已完成任务数 / 已到达任务总数 |
| 平均完成时延 | 对已完成任务计算 finish_time - arrival_time 后求平均 |
| 按时完成率，补充项 | 截至 H 已按各自截止时间完成的任务数 / 已到达任务总数 |
| 资源利用率 | 每种资源实际用于有效步骤的时间 / 该资源可服务时间；可服务时间为观察时长减故障/关闭时长 |
| 资源占用率，补充项 | 资源可服务期间被任务持有的时间 / 可服务时间，包含占着等待的时间 |
| 资源冲突次数 | 因资源已被任务占用而新进入等待的次数；同一次连续等待不每步重复计数 |
| 安全性拒绝次数，补充项 | 因银行家安全性检查拒绝的新等待次数，与资源冲突区分 |
| 死锁次数 | 新出现的死锁事件数；同一组任务构成的环未解除期间不重复累计 |
| 紧急任务错失率 | 截止时间不晚于 H 的紧急任务中，未按时完成的数量 / 这些紧急任务总数 |
| 回滚成本，补充项 | 因回滚导致的实际重做工作量、回滚次数及撤销数 |

平均时延只看完成任务可能掩盖未完成任务，因此必须同时给出完成率、未完成数及未完成任务已等待时间。没有完成任务时平均时延记为空值，不记为 0；没有符合条件的紧急任务时错失率也为空值。资源可服务时间为 0 时利用率为空值。

对于不同实验组使用固定 H 作为结果统计窗口，提前结束后空闲时间仍属于窗口；不让各组自行缩短分母。故障期间持有资源的记录仍保留，但有效工作为零。资源利用率按资源分别报告，若汇总则注明是四种资源的简单平均。

## 11 对比实验

### 11.1 场景族

1. 小型正确性场景：少量任务，人工算得出顺序和完成时间。
2. 普通负载：请求分散，大部分任务可完成。
3. 台面拥堵：多个维护任务集中争用 TABLE。
4. 紧急请求：普通任务执行中插入紧急送水任务。
5. 环境与故障：固定时刻关闭和恢复某资源。
6. 死锁压力：用明确的相反资源申请顺序验证避免、检测、破解。
7. 前置依赖：前一项未完成，后一项不得执行。

### 11.2 对照设计

| 实验目的 | 对比变量 | 控制条件 |
|---|---|---|
| 评价排序策略的影响 | FCFS / 优先级 | 输入、资源、H、死锁与抢占设置 |
| 评价抢占机制的影响 | 抢占关闭 / 开启 | 排序规则、事件、任务步骤、资源 |
| 评价动态重调度的影响 | 静态队列 / 事件后动态重排 | 初始任务、未来事件、抢占设置、死锁设置 |
| 评价死锁机制的效果与代价 | 无保护 / 检测恢复 / 避免加检测恢复 | 同一资源申请场景、任务、观察窗口 |

涉及抢占、紧急请求的场景必须确实存在可抢占步骤和相关事件，否则可能没有区别。死锁检测可在各组都开启作为观测工具；是否恢复和是否避免分别用开关控制。基线不强制额外加载全部保护机制，结果中逐项注明。

实验首先使用固定案例验证正确性，再使用随机种子 1—20 生成 20 份独立负载，各方法复用相同负载。该规模为初始实验配置，可根据运行成本调整，调整结果应完整记录。重复运行同一确定性输入不计为独立样本。

报告各组样本数、平均值及标准差，保留全部运行结果。结果分析应同时反映收益与代价，包括紧急任务改善对普通任务等待的影响，以及安全性检查对并发程度的影响。

## 12 数学模型要求

李和雨负责定义并与代码负责人核对：

- 任务 Ti = (到达时间 ai，优先级 pi，截止时间 di，步骤集合 Si，依赖集合 Di，可抢占标记 qi)。
- 完成时延 Li = Ci - ai，其中 Ci 为完成时刻。
- 截止时间满足条件 Ci ≤ di；未按时完成不能算按时成功。
- 每种资源 r 的占用量满足 Σi xir(t) ≤ capacity(r)；互斥资源容量为 1。
- 前置任务 j 属于 Di 时，i 的开始不得早于 j 的完成。
- 银行家算法使用 Need = Max - Allocation，并说明安全性检查流程。
- 本文第 10 节的评价公式和分母口径。

数学模型用于描述任务约束、资源限制、算法条件和评价指标。项目采用规则调度与实验对比，研究内容表述为“面向茶歇场景的调度与资源管理方案及实验验证”。涉及最优性或新颖性的结论，应提供相应证明或文献依据。

## 17 最终验收标准

### 程序

- 普通任务可以跑完，执行时间可手工核对。
- 茶歇台等互斥资源不会违规重复分配，资源与任务账目一致。
- 前置依赖、截止时间、抢占条件都有实际作用。
- 冲突、危险申请、死锁、故障等待能正确区分。
- 回滚释放真实资源，重做成本真实计入，恢复后没有重复完成任务。
- 三类中断可触发，有保存与恢复记录。
- 即使死锁未解除也能到 H 正常导出结果，不让程序无限挂住。

### 实验和报告

- 对比组的唯一差异及其余固定条件有记录。
- 原始结果包含任务结局、配置、随机种子和对应代码版本。
- 图表可由原始数据重新生成，没有虚构数字或预先保证的优势。
- 论文描述实现了的内容；限制、失败和代价如实呈现。
- 报告使用教师模板，删除示例正文、图片及过期目录占位。
- 每个成员交自己的材料，分工与实际贡献一致。

### 演示

- 能在目标 Ubuntu 22.04 环境按说明启动。
- 至少演示普通调度、资源竞争、死锁避免、死锁检测与破解、事件中断及一组对比结果。
